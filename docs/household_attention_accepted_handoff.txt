Recommendation
Build one HA-owned household attention handler shared with the Bravia notice design. Purpose confirmed by Lachlan on 14 November: tell me there is a problem, or I need to do something. Capture faults, chores, approvals and maintenance needs (including stale credentials), with per-source records and destination rules. Existing automatic fixes are independent consumers of the same underlying conditions, not prerequisites for creating attention records. Keep source observation, incident lifecycle, automatic remediation and notification delivery separate. Derive operational health only from fault records, not from washing tasks or available updates.

Coverage and missing-detector matrix
Internet — Monitor disconnected/off or unavailable connectivity as an attention condition, with source-specific state interpretation. This belongs in the shared HA inbox/dashboard even though the existing NBN power-cycle automation may repair it. Recovery resolves the same incident; an attempted repair does not. Repeated source reports/repair attempts do not create duplicate incidents. Delivery debounce and severity are policy choices separate from capture. External phone delivery may fail during an outage. Keep automation 1786235041388 unchanged.
Kiosk — Monitor actual kiosk phone reachability/availability, independently of automation 1789173535286. Lachlan recalls an online/offline entity; its existence, semantics and freshness need verification rather than assumption. Phone power-off/offline deserves a shared notice, TV card and probably phone alert. Charger switch on does not prove the phone is alive; stale battery percentage alone does not prove it is dead. The charging watchdog remains an independent existing solution. Do not add a second charger controller or gate notices on its failure.
Washing — Existing completion event and cleaning-count notifications are useful accepted Phase 3 sources. Missing: typed occurrence capture, deduplication and expiry. A completed wash is an informational event, not a home fault. Keep phone notifications and laundry lighting intact during capture-only work.
Backups — No monitored failure/staleness detector found. Accepted Phase 3 source and best first fault lifecycle example. Need exact installed backup entities/events, configured cadence, expected completion time and recovery evidence. A successful backup can resolve a failure only under an explicitly defined matching policy; starting one is insufficient.
Updates — No grouped attention record found. Phase 3 requires one summary, distinct component/version details in the private inbox, removal as confirmed updates clear, and no per-component phone alerts. Unknown states mean incomplete coverage, not zero available updates. Updates are attention items and should not automatically degrade household operational health.
Thread/dependency recovery — Repository records the household interruption where HA/photos worked but the user manually recovered Thread and SSH. Missing: verified required-dependency inventory, startup grace and dependency grouping. Phase 6 candidate. SSH is optional maintenance and must not be assumed permanently required. A running add-on alone does not establish usable Thread lighting.
Device availability — Use a curated device/source map including the user’s examples: internet, Dyson fan, fridge and kiosk phone. Off means disconnected for some connectivity sources but is a normal operating state for a fan/light; interpret per source. An unavailable entity is a useful HA visibility problem even when physical device failure is unproven. Say 'HA cannot reach the fridge' rather than claim cooling stopped. Distinguish unknown/missing monitoring data in record wording/quality; never treat it as healthy. Group multiple entities for one device and known shared-dependency failures. Exclude deliberate maintenance/sleeping/intentional disconnection. Previous general persistence proposal was more than one hour; whether fridge/kiosk/internet need shorter notification delays is unresolved. Capture and delivery timing are separate; duration gates should not erase source evidence.
HA/Pi/power outage — An HA-hosted foundation cannot reliably report its own complete outage. Independent monitoring is a separate optional design; not included or promised here.
Small native model
Implementation choice remains open after the 14 November comparative research below. Compare Alert2 with a small native HA implementation before committing to source-specific restored template records; evaluate Supernotify only if needed for delivery. Keep one clear owner for each attention record and a stable HA-facing contract for inbox/TV consumers. Validate feasibility, reconciliation and persistence against installed versions. Restoration is continuity, not a fresh observation or guaranteed archival durability.
Proposed minimum fields: stable incident key; occurrence identity; category; kind (fault/event/attention); severity; active/resolved lifecycle; observation quality (valid/unknown/stale); first detected, last valid observation and resolved timestamps; concise text; source reference; optional dependency parent. Keep previously active incidents active when evidence becomes unknown, with their observation quality marked uncertain. Healthy→unknown becomes a monitoring gap, not an invented physical failure. Maintenance suppresses routing/evaluation as explicitly defined; it does not manufacture recovery.
Repeated failure observations update one occurrence. A verified recovery resolves it. A later genuine failure starts a new occurrence. Do not replace occurrence IDs or first-seen timestamps on each periodic check. Separate active faults from retained history and expiring one-off events. A finite prototype retains the current/last occurrence only; unbounded searchable history needs an explicit retention design.
Derive active-fault count and category/overall health; never let independent detectors set and clear one global boolean. Report coverage separately: e.g. no confirmed faults with 2 sources unknown. Do not show an unqualified green/healthy state when required observations are incomplete. Destination preferences remain restored everyday HA controls; phone delivery cannot depend on the TV/photo host.

Research conclusion and implementation decision
The architecture is supported by existing approaches: source-specific detection, independent attention state, and delivery policies for people, presence and destination. This is an engineering assessment from the documented examples, not a live validation on this household. The earlier requirement to use only restored template records was premature. Compare existing tools before choosing or building the foundation; no package installation is approved or performed by this research.
Alert2 is the strongest first candidate for the attention lifecycle: it supports both condition and event alerts, acknowledgement/reminders, notification controls and alert hierarchies. Its supersedes feature suppresses subordinate notifications; it is not proof of a shared physical cause. Documentation warns that recently fired alerts can be lost across restart because restoration is periodically saved. Test restart/reconciliation and do not assume archival durability. Determine how its exposed state could feed the HA/TV record contract.
https://github.com/redstone99/hass-alert2/blob/master/README.md
Supernotify is a routing candidate if it materially reduces custom configuration: occupancy can filter individual recipients, and deliveries can have priority/condition constraints. Its duplicate check is a short-lived message cache, cleared on restart, and normalises digits; this cannot replace stable device/incident identity. Evaluate it as an optional delivery layer, not a competing incident store. Alert2 plus small native routing scripts should also be compared; no need to adopt two integrations automatically.
https://supernotify.rhizomatics.org.uk/latest/configuration/deliveries/
https://supernotify.rhizomatics.org.uk/latest/configuration/dupe_detection/
Blacky’s Appliance Notifications & Actions blueprint provides a concrete comparable example: completion/reminder notifications, device-zone recipient filtering, dashboard run status and custom actions. Borrow its treatment of “finished and still needs attending” and independent outputs; do not replace the existing working washing detector merely to adopt a blueprint.
https://community.home-assistant.io/t/appliance-notifications-actions-washing-machine-clothes-dryer-dish-washer-etc/650166
Blacky’s Low Battery Notifications & Actions supports battery thresholds, exclusions, independent groups and separate low/unknown/unavailable handling. It does not establish a reliable rapid-drain detector for these switches. Verify the actual battery entity and history before defining a significant drop and measurement window; missing data is not 0%.
https://community.home-assistant.io/t/low-battery-notifications-actions/653754
Watchman is useful for broken configuration references, not complete device monitoring: it checks references it finds in configuration and acknowledges heuristic misses/false positives. Spook’s Repairs extension exposes repair changes and counts, offering a candidate source for actionable repair/authentication problems. Verify the installed version, issue content and whether each integration exposes reauthentication through this path; not every expired credential is guaranteed to appear.
https://github.com/dummylabs/thewatchman

Do not poll it or create attention records for it in this handler; normal HA integration processing is outside that promise. Prefer relevant entity changes and targeted reconciliation over repeated whole-instance scans.
Keep one device/household attention item with its supporting evidence. For the fridge, plug unavailable OR LG unavailable is sufficient; retain which source failed. The item cannot clear just because one channel is healthy while the other remains unavailable. Do not conflate loss of visibility with proof cooling has stopped, or clear a physical-cooling concern using mere connectivity recovery.
Combinations need explicit policies: members of a light group; both Dysons; fridge plug plus LG; many devices failing behind one integration or network dependency. Correlate only with evidence. Grouping should reduce duplicate notices while retaining affected devices; never silently suppress the fridge’s agreed phone route behind a generic internet alert.

Build handoff — accepted direction and recommended workflow, 14 November 2026
Accepted product boundary
Source rules are maintained through conversation with Lachlan or another agent and stored as reviewed configuration. Delivery preferences are everyday HA UI controls, initially set together and subsequently editable quickly without a code change. One row represents device plus attention type; washing finished and washer unavailable are different rows.
Each row has six independent destinations: HA dashboard; TV screensaver; Lachlan phone when home; Lachlan phone when away; Nic phone when home; Nic phone when away. The inbox remains the underlying record even if every destination is off. Dad’s desk plug is excluded at source, not merely silenced. Laundry lighting is an additional controllable action rather than a seventh phone destination.
Definitions, source rules and routing logic belong in Git; user-selected preference values belong in restored HA runtime state. Deployment, restart or source-rule updates must not reset the selected values. Dashboard/TV changes re-filter active items; newly enabled phone destinations must not cause an unexpected backlog resend. Presence is per recipient, with explicit stale/unknown handling. Temporary category/channel pauses are a desired convenience, with automatic expiry and preserved previous settings. Final pause scope/behaviour can be refined in UI review.
Notifications and record tracking run deterministically in HA; an AI conversation is for maintaining source rules, not a required runtime dependency. Existing auto-repair automations stay independent.
